## Training-loop findings

**Verified, TD-MPC adaptation:** exactly625 episodes×80=50,000 steps; first100 actions uniformly random, remaining60 actions of episode2 use an untrained planner. First100 updates occur after replay insertion at160 steps, then80 updates per completed episode. Total100+623×80=49,940. First update schedule indices80..179 overlap next episode's160..239; the count is a distinct quantity from the schedule index. Horizon changes at episode boundaries; learner rollout length stays20 throughout. Target update cadence uses that schedule index, not the update counter.

**Inference from original loop:** literal upstream `range(0, train_steps+episode_length, episode_length)` would collect an extra episode; with seed_steps100 and episode_length80 the equality `step == seed_steps` is never reached. Its warmup/pretraining behavior would differ. The custom runner makes the budget explicit and changes warmup semantics; this is an adaptation/confound, not a hidden change to the native losses. Cannot claim exact original runner reproduction.

**Verified, TD-MPC2:** cfg.steps49999 compensates the inclusive upstream loop to50,000 actions. Random actions occur for _step0..1000 (1001 actions), 1000 pretraining updates follow action1001, then one per step1001..49999:49,999 updates. At pretraining replay contains12 complete episodes (960 transitions); incomplete current episode is not sampled. Episode insertion happens on the next loop's done branch. Final80 transitions are never inserted before exit; this is the native loop boundary behavior. Buffer receives steps50000, holds50,000 rows rather than transitions;624 completed episodes occupy50,544 rows, so old rows are evicted. SliceSampler prevents crossing episode IDs. Pilot-only expanded capacity is NOT used in this full run.

## Patch audit

**Verified application checks:** all patches apply to disposable copies of exact pinned sources (patch_verification.json). Pins remain clean.

- patches/tdmpc_device.patch: configurable device, mapped safe weight loading, replay tensor transfers. No equations, target cadence or sampling weights changed.
- patches/tdmpc2_fluidgym_task.patch: environment factory registration; Gymnasium logging API fallback; forwarding max_episode_steps. Also functional Ensemble compatibility: to_module replacement semantics and skipping meta templates during device traversal. This affects implementation mechanics/autograd and is more than logging; intended to preserve original gradients. Existing CPU regression compares weights, forward values, gradients and target templates when TensorDict is installed. See actual test log for executed/skipped status; no blanket historical version-equivalence claim.
- patches/tdmpc2_logging.patch: W&B group/tags and config serialization only. Observer wraps calls to count/time/synchronize metrics; logging adds periodic saves and final eval. Timing changes and additional evaluation RNG consumption can affect execution, though no optimizer objective is changed.

**Verified reproducibility defect (current source):** FluidGymTDMPC2Env constructs a fresh Box action_space but never seeds it. TensorWrapper.rand_act samples that independent generator; common.seed.set_seed does not seed new Gymnasium spaces. The fake-env audit explicitly checks `_np_random is None` after construction. Seed1 alone cannot fully reproduce warmup actions. Historical training source completeness limits absolute historical attribution. **Hypothesis, untested:** this contributed materially to the performance gap. Do not fix silently; any future correction must define a new run protocol.

**Verified:** TD-MPC2 cfg reward/value targets, SimNorm and sampled2-of5 Q aggregation are native differences. Different horizon/latent size/lr cannot by themselves establish unfairness or a causal error. This is an adapted native-algorithm comparison; matched-variable experiments would be separate controlled ablations requiring their own claims.
